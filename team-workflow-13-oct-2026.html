Key takeaways

  1. Draft PR on day one. The branch exists when the PR exists. No PR, no work.
  2. "Ready" is the complete body: commands run, iOS and Android named, risk and not-done, a real AI-assisted line. CI checks it, and blocks the merge once the check is required (Part D).
  3. Small and single-purpose: under ~400 lines, one concern; native changes and tooling bumps in their own PR.
  4. Stack at most two. Merge bottom-up, rebase after each merge (AI agents merge develop in instead), next branch from develop.
  5. One working day: review after "Ready", answers to comments the same day; two code owners per repo so nobody waits on one person. With auto-merge on, an approved, green PR merges itself.
  6. The board is the status. Draft, Ready for review, Changes requested, Merged; nothing else needs asking.
  7. The flow itself is unchanged: branch → develop (squash) → uat → main + prod-YYYY.MM.DD, releases by the CTO.

Part A. The workflow we have today

This is the flow as written in the engineering guide and enforced by GitHub since 2026-10-08. Nothing in it is wrong; Part B changes how we work around it, not the flow itself.

How a change moves today

  1. Start from the latest develop: git switch develop && git pull && git switch -c feature/<topic>.
  2. Commit (type(scope): summary), then git push -u origin feature/<topic>.
  3. When the work is done, open a PR into develop. The title follows the commit format; CI checks it.
  4. Fill the PR template: what changed, how you verified it, risk, AI-assisted yes/no.
  5. Keep PRs small: aim for under ~400 changed lines (lockfiles do not count). Split big work.
  6. CI must be green: standard / pnpm only, standard / secret scan (new commits), standard / PR title is type(scope) summary, the repo's own checks; the AI review comments but never decides. Then the code owner approves and merges with Squash and merge.
  7. After the merge: git switch develop && git pull, start the next branch from there.
  8. Releases (CTO): develop → uat PR with a merge commit (UAT deploys), then uat → main PR with a merge commit and the tag prod-YYYY.MM.DD (production deploys the tag). Hotfix from main, merged back the same day.

Mobile changes are verified on iOS and Android before the PR is opened, per the guide; AI agents work on feature branches only, mark the PR AI-assisted, and never merge, promote or deploy.

Part B. What we change

The branches, the protected develop → uat → main flow, squash merges into develop, merge-commit promotions and the dated production tag all stay exactly as they are. The changes are in how we work around that flow.

Part C. The workflow from 2026-10-13

Everything below is the full workflow with the changes applied; this is the reference from now on.

1. The flow

2. Your day, step by step

  1. Start from fresh develop. git switch develop && git pull && git switch -c feature/<topic>. Name the branch by what it does: feature/booking-reminders, fix/otp-timeout, chore/pnpm.
  2. Open a draft PR the same day. git push -u origin feature/<topic>, then "Create draft pull request" (or gh pr create --draft --base develop) with the title (type(scope): summary) and one line on the goal. From now on the work is on the board; nobody has to ask.
  3. Commit small, push daily. One logical change per commit, message type(scope): summary. A branch that exists only on your laptop has no backup and no review.
  4. Verify. Run the repo's verify commands (see its AGENTS.md). App change: run it on iOS and Android, every time.
  5. Make it ready. Fill the template (section 3), press "Ready for review". CI checks the body again; fix anything red.
  6. Review within one working day. A code owner reads it, the AI review comment is advice for both of you. Answer comments the same day and resolve every thread. Merge is Squash and merge: by auto-merge if you turned it on, otherwise by the reviewer.
  7. Next branch from develop, not from the open PR (see stacks, section 5).

3. What "ready" means

The PR body is the contract. CI checks it (standard / PR body is complete): How I verified it and Risk must not be empty, the AI-assisted line must say yes or no (the template's yes / no placeholder fails), and in app repos the - iOS: and - Android: lines must be filled. The other sections are checked by the reviewer.

SectionWrite
What changedWhat and why, in a few lines. Link the task if there is one.
How I verified it- Commands: the exact commands you ran (typecheck, lint, tests).
- iOS: device or simulator and OS version, or "not a mobile change".
- Android: device or emulator and API level, or "not a mobile change".
RiskWhat could break, what the reviewer should read most closely, and what is not done. Silence is not allowed; "not done: X" is. Over ~400 changed lines: a Size: line with the reason.
ChecklistTitle format · no secrets · pnpm only · tests for new logic · under ~400 lines or the reason in Risk · native change alone in its PR · mobile on both platforms.
AI-assistedAI-assisted: yes (tool) or AI-assisted: no. If yes: what the agent verified by actually running it. You own every line the agent wrote.

Size and scope

  • Do keep a PR under about 400 changed lines (lockfiles do not count). Bigger work is split into PRs that each leave the app working.
  • Do put a native change (Expo config plugin, app.json, patches/, ios/, android/, permissions) in its own PR, with the dev-client or EAS build that proved it named in the body.
  • Do put a tooling bump (test library major, package manager, CI) in its own PR.
  • Don't bundle six fixes, a native change and a dependency bump in one PR. It will be sent back to be split.

Drafts skip the body check, so open the draft early without worrying about the template. Pressing "Ready for review" runs it again (once each repo's standard.yml listens for ready_for_review, Part D).

5. Stacks (work that depends on an open PR)

  • At most two PRs on top of each other, and the bottom one must be ready.
  • Merges go bottom-up. After each merge, rebase the next PR onto develop and push. AI agents merge develop in instead, because they never force-push.
  • If you need a third, stop and get the bottom one merged, or split differently. A deep stack means every PR carries every PR below it, and one change request freezes all of them.

6. Review

As the author
  • "Ready" only when section 3 is true. A half-filled body wastes the reviewer's slot.
  • Answer every comment the same day: fix it, or say why not in the thread.
  • Read the AI review comment; fix what is right, say what is wrong. It does not decide.
As the reviewer (code owners)
  • First read within one working day of "Ready".
  • Check: description matches the diff · CI green (the AI review never blocks) · no secrets or extra lockfiles · tests for new logic · both platforms named for app work · one concern per PR · Risk says what is not done.
  • Never approve a PR you prompted an agent to write.
  • Approve. If the author turned on auto-merge, it merges itself; otherwise Squash and merge. The branch is deleted automatically.

7. Releases (CTO)

  1. develop → uat: PR titled chore(release): uat YYYY-MM-DD, merged with a merge commit. UAT deploys; testers test there.
  2. uat → main: PR titled chore(release): prod YYYY-MM-DD, merge commit, then tag prod-YYYY.MM.DD; production deploys that tag. Rollback is the previous tag.
  3. Hotfix: hotfix/<topic> from main, PR into main, tag, then main merged back into uat and develop the same day.
  4. Mobile store builds come from main at a tag app-vX.Y.Z; UAT builds from uat.

8. The board

Every open PR in the org is on one GitHub Project with four columns: Draft, Ready for review, Changes requested, Merged. It is the only status report. If something is not on it, it does not exist yet; if it is in Draft for more than three working days, split it or ask for help.

9. AI coding agents

  • Agents work on your branch only. They never merge, promote, deploy, force-push, approve or turn on auto-merge.
  • An agent may push and open the draft. It marks the PR ready only after you have reviewed the full diff and told it to.
  • Mark the PR AI-assisted: yes (tool) and list what the agent verified by running it.
  • Review every line before "Ready" as if you wrote it. The reviewer is never the person who prompted the agent.
  • No dead code "for later", no leftover TODOs or debug logs; the reviewer sends it back.

Why these changes

The flow itself did not change. Six practices did, after the first week showed what happens without them: a 16-deep stack of PRs that could not be merged, branches nobody could see, app PRs tested on one platform, native changes hidden inside QA fixes, and releases that needed admin bypasses.

  • Draft PR on day one (new).
  • "Ready" defined and checked by CI (new).
  • Stack limit of two (new).
  • Second code owner on each repo, so a PR never waits on one person (new).
  • Review within one working day, tracked on the board (new).
  • Backend tests now run in CI; app PRs must name both platforms (new).

Questions or a rule that does not fit your repo: open a PR against paperplanehq/paperplane-engineering. The guide changes the same way the code does.
