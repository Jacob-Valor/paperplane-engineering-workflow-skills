# Open questions for the CTO

The skills follow the engineering guide. Where they add a rule the guide does not state, the skill
labels it `(team convention, not in the guide)`; where they read the guide one way among several,
they say so. Each row below needs a yes, a no or a correction. Until answered, agents use the safe
default (the more restrictive reading). Line numbers refer to the files at this commit.

| Rule | Where it lives | Current behaviour | Question for the CTO | Safe default if unanswered |
|---|---|---|---|---|
| Opening a draft release PR is "preparation", not "promotion" (guide §7) | `releasing › Overview` | Agents open draft `develop`→`uat`, `uat`→`main`, hotfix and merge-back PRs; they never merge or tag | May agents open these draft PRs, or must a person open them? | Agents open drafts only and never merge, tag or deploy |
| Release-PR approver when the CTO prompted it | `releasing › CTO runs` ("Approval"), `reviewing-prs › Overview` | The other code owner approves; the CTO then merges and tags (guide §4, §7 give no release exception) | Is the other code owner approving a release PR you prompted acceptable, or is there an exemption? | The other code owner approves |
| Mobile store builds come from `main`; `uat` only gives UAT builds; the CTO or release owner starts the build and tags `app-vX.Y.Z` | `releasing › Mobile store builds` | Agents write out the commands and never start a store build | Which branch do store builds come from, and who starts them? | Agents never start store builds; commands are written for `main` |
| Auto-merge: agents never turn it on; allowing it in repo settings is optional | `shipping-changes › Hard rules`, `reviewing-prs › Overview`, `repo-setup › Audit`, `repo-setup › Settings` | Agents never enable it; repo-setup leaves `--enable-auto-merge` out of the standard command and names it as CTO-optional (source: the org templates, not the guide); `audit.sh` flags it | Is auto-merge part of the standard? May authors use it? | Not part of the standard; agents never turn it on |
| Rebase merge disabled in repo settings | `repo-setup › Audit`, `repo-setup › Settings` | repo-setup names `--enable-rebase-merge=false` as CTO-optional, not in the standard command; `audit.sh` checks it | Should rebase merge be off? | Leave it as the CTO sets it |
| Rulesets `protect-develop-uat-main` and `release-tags-owner-only` and their details (1 code-owner approval, green `standard / checks`, only org admins create `prod-*` tags) | `releasing › Overview`, `repo-setup › Overview`, `repo-setup › Settings` | Agents never create per-repo protection; `audit.sh` checks the ruleset by name | Are these the right names and settings? | Agents do not create or edit rulesets; they report a missing one |
| Reviewer blocks on leftovers: dead or commented-out code, "for later" helpers, TODOs, debug logs | `reviewing-prs › Checklist` ("Leftovers"), `shipping-changes › Workflow` (step 7 "Ready") | Reviewing agents list them as blockers; shipping agents remove them before Ready | Should these block a PR, or only be raised as comments? | Remove them before Ready; report them as blockers |
| All review threads resolved before merge | `reviewing-prs › Checklist` ("Review threads") | An open thread is a blocker | Is this a rule, or only a ruleset setting? | Treat as a blocker |
| A draft open more than three working days gets split (guide: "days, not weeks") | `shipping-changes › Workflow` (step 9 "Old drafts") | The agent tells the user and stops adding to the draft | What is the limit, if any? | Three working days |
| Allowlisting a gitleaks finding needs the CTO's approval | `secret-incidents › When the secret scan flags a commit` (step 2), `shipping-changes › Hard rules` | Agents never edit `.gitleaksignore` or add `gitleaks:allow` on their own | Do you want to approve every allowlist entry? | The CTO approves every entry |
| Only a stricter `AGENTS.md` can override org policy; a narrower one cannot (iOS and Android verification) | `reviewing-prs › Checklist` ("Mobile"), `shipping-changes › Overview` | Mobile PRs need both platforms even if a repo's `AGENTS.md` narrows it | May a repo's `AGENTS.md` narrow the guide (for example a web-only app)? | Both platforms always |
| An agent may prepare a local history rewrite for a pushed branch with a leaked secret; a person force-pushes | `secret-incidents › When the secret scan flags a commit` (step 4 "History") | The agent does a local fixup and autosquash, then stops | Is a local rewrite by an agent acceptable, or must a person do all of it? | Agent prepares locally and never pushes |
| `corepack use pnpm@10` for migrations (the guide names no pnpm version; `pnpm approve-builds` needs pnpm 10+) | `repo-setup › pnpm migration` | Migration PRs pin pnpm 10 | Which pnpm major should repos pin? | pnpm 10 |
