# Open questions for the CTO

The skills follow the engineering guide. Where they add a rule the guide does not state, the skill
labels it `(team convention, not in the guide)`; where they read the guide one way among several,
they say so. Each row below needs a yes, a no or a correction. Until answered, agents use the safe
default (the more restrictive reading). Line numbers refer to the files at this commit.

## Team conventions and readings

| Rule | Where it lives | Current behaviour | Question for the CTO | Safe default if unanswered |
|---|---|---|---|---|
| Opening a draft release PR is "preparation", not "promotion" (guide §7) | `releasing › Overview` | Agents open draft `develop`→`uat`, `uat`→`main`, hotfix and merge-back PRs; they never merge or tag | May agents open these draft PRs, or must a person open them? | Agents open drafts only and never merge, tag or deploy |
| Release-PR approver when the CTO prompted it, in a unit with a second code owner | `releasing › CTO runs` ("Approval"), `reviewing-prs › Overview` | The other code owner approves; the CTO then merges and tags. A unit with no second code owner follows guide §4 (the CTO is the only approver and merges their own PR with `--admin`) | Is the other code owner approving a release PR you prompted acceptable, or is there an exemption? | The other code owner approves |
| Mobile store builds come from `main`; `uat` only gives UAT builds; the CTO or release owner starts the build and tags `app-vX.Y.Z` | `releasing › Mobile store builds` | Agents write out the commands and never start a store build | Which branch do store builds come from, and who starts them? | Agents never start store builds; commands are written for `main` |
| Auto-merge: agents never turn it on; allowing it in repo settings is optional | `shipping-changes › Hard rules`, `reviewing-prs › Overview`, `repo-setup › Audit`, `repo-setup › Settings` | Agents never enable it; repo-setup leaves `--enable-auto-merge` out of the standard command and names it as CTO-optional (source: the org templates, not the guide); `audit.sh` flags it | Is auto-merge part of the standard? | Ruleset `protect-develop-uat-main` and its details (1 code-owner approval, green `standard / checks`) | `releasing › Overview`, `repo-setup › Overview`, `repo-setup › Settings` | Agents never create per-repo protection; `audit.sh` checks the ruleset by name. | A draft open more than three working days gets split (guide: "days, not weeks") | `shipping-changes › Workflow` (step 9 "Old drafts") | The agent tells the user and stops adding to the draft | What is the limit, if any? | Three working days |

## Where the guide disagrees with itself

Found while matching the skills to guide v2.2 (`paperplanehq/paperplane-engineering` at `develop`, 2026-11-14). The skills
follow the code that runs (CI and conformance) where the prose differs.

| Topic | Prose says | Code or template does | Skills do now | Question for the CTO |
|---|---|---|---|---|
| PR size | README §4 "From standard v2": over 400 lines "fails unless the body has `Size exception: <reason>` and a code owner adds the label" | `standard-checks.yml` only warns, and accepts `under ~400`, `size:`, `why not` or `one mechanical change` in the body; `Size exception: x` does not match, so it still warns | Write `Size: <reason>` (`shipping-changes › Workflow`, `reviewing-prs › The gate`) | Should size fail with a label, and which body wording counts? |
| `Agent:` and `Prompted-by:` lines | README §4: "the PR template gains `Agent:` and `Prompted-by: @login`" | `templates/pull_request_template.md` has neither line; no check reads them | `AI-assisted: yes (<tool>) — <what ran>` names the tool; the prompter is not written | Add the lines to the template (and a check), or drop them from the README? |
| CODEOWNERS approvers | README §4: "the two approvers in `CODEOWNERS`" | `templates/CODEOWNERS` ships one placeholder (`@pay-tbd`); conformance C02 needs one owner; README §4 also allows one approver until a unit has a second | `audit.sh` fails a placeholder or a missing owner and warns on one owner (`repo-setup › Audit`) | Is one owner per line acceptable as the standard? |
| Action pinning | Conformance C07: third-party actions pinned to a commit SHA | `templates/terraform.yml` uses `actions/checkout@v4`, `hashicorp/setup-terraform@v3`, `terraform-linters/setup-tflint@v4`, `aquasecurity/trivy-action@v0.36.0`: a repo that copies it fails C07 | Pin them to SHAs in the copy (`repo-setup › Standard v2 conformance`) | Pin the template in the guide repo? |
| AGENTS.md standard block | README §7: "The first block of `AGENTS.md` states …"; conformance C05 looks for `<!-- paperplane:agents-block` | The block text lives in `paperplane-platform` `docs/standard/governance.md`, which most developers cannot read; no repo in the org carries the marker yet | Copy it from a sibling that has the marker, else ask the CTO; never write one (`repo-setup › Files`) | Publish the block in `paperplane-engineering/templates/`? |
| Rollback in a `unit-deploy` repo | README §8: the CTO deploys; nothing on rollback | `unit-deploy.yml` deploys on a `uat` push or a pushed `prod-*` tag only, with no manual trigger; an old tag already exists, so it cannot be pushed again | "Rollback means deploying the `prod-*` tag before the bad one" (`releasing › CTO runs`) | How is a previous tag redeployed: re-run its deploy run, or a manual trigger? |
